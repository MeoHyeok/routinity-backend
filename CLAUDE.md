## Architecture

### Data model
Four core tables, all keyed off `user_id` referencing Supabase Auth's `users` (migrations under `supabase/migrations/`):
- `routine_logs` — event log of routine actions (`type`: `wake | sleep | meal_start | meal_end | study_start | study_end`, plus the deprecated `meal` — see API surface) with a `timestamp`. This is the raw input everything else derives from. Deletable by owner (`DELETE /logs?id=`).
- `goals` — per-user target values (`target_type`: `wake_time | study_duration`, etc., not a fixed enum) that logs are scored against. Upsert semantics: at most one row per `(user_id, target_type)`. Deletable by owner (`DELETE /goals?target_type=`). `created_at` (added 2026-08-14) is set once on insert and untouched by the upsert's update path — `/insights` uses it to exclude days before a goal existed from its aggregates (see Scoring logic).
- `ai_reports` — generated daily/weekly/monthly AI report text, derived from `routine_logs` + `goals` (`period` check constraint widened 2026-08-14 to add `monthly`). All three periods are generated at most once per KST day and cached (`generated_via: "claude" | "template"`), enforced by a shared `(user_id, period, KST day)` unique index that predates `daily`/`monthly` actually being used — no caching-logic changes were needed to add either. The index was originally `(user_id, period, UTC day)`; migrated to KST on 2026-08-18 (`20260818060000_ai_reports_kst_day_dedup.sql`) alongside the day-boundary fix below — a UTC-anchored index would otherwise let a concurrent cache-miss race near the 09:00 KST rollover insert two rows for what the app now considers the same day.
- `rate_limits` — added later (Day 13-14 work) to back the fixed 1-minute-window rate limiter; not part of the original four-table plan.

All four tables have RLS enabled with owner-only policies (`create policy ..._select_own` / `..._insert_own` etc. in `supabase/migrations/20260810062033_init_schema.sql`, `20260810084732_rate_limits.sql`, and `20260814070000_add_delete_policies.sql` for the delete policies) — a user can never see or delete another user's rows.

### API surface
Edge Functions are served under `/functions/v1/<name>` (Supabase's standard prefix), not the flat `/logs`-style paths sketched in the ROADMAP draft: `/functions/v1/logs`, `/functions/v1/goals`, `/functions/v1/scores`, `/functions/v1/reports-weekly`, `/functions/v1/reports-daily`, `/functions/v1/reports-monthly`, `/functions/v1/insights` (the last three added 2026-08-14, not in the original ROADMAP draft — see AI feedback / Scoring logic sections). `/logs` and `/goals` also support `DELETE` (added 2026-08-14 at the iOS team's request — not in the original ROADMAP draft) for removing a mis-logged entry or dropping a tracked goal entirely. `/logs`' accepted `type` values changed 2026-08-17: the home screen moved from 4 log buttons to 3 (기상/식사/공부), adding `sleep` and `meal_start`/`meal_end` and dropping `meal` from what new `POST`s accept (still valid to read — see Scoring logic § day breakdown). Auth is a required `Authorization: Bearer <access_token>` header (401 if missing/invalid); errors are `{ "error": "..." }`. See `docs/api-contract.md` for full request/response shapes — it is the field-name/type source of truth for the iOS team, finalized from the ROADMAP draft (e.g. log `id` is a uuid, not the draft's `log_abc123`). Per the roadmap, any further field/type change must be announced to the team channel immediately.

### Scoring logic
`supabase/functions/_shared/scoring.ts` is a pure-function layer that compares `routine_logs` against `goals` to produce a per-day score with three outcome cases: achieved / not_achieved / missing. Currently implements rules for `wake_time` and `study_duration` only; other `target_type` values are silently excluded from `/scores` output until rules exist for them. `computeDailyScore` (added 2026-08-14, design confirmed with the iOS team) rolls a day's `ScoreEntry[]` into one 0-100 `daily_score` on the same response — `null` when there's nothing to score. Uses per-goal partial credit rather than a binary achieved-count ratio (which only ever landed on 0/50/100 with just 1-2 scorable goals): `achieved` = 1, `missing` = 0 (no data to judge closeness), `study_duration` `not_achieved` = actual/target minutes ratio, `wake_time` `not_achieved` = linear decay over a 120-minute lateness window.

`goalsExistingBy` filters a goal list down to only goals whose `created_at` predates a given cutoff — without it, a currently-set goal retroactively scores as "missed" every day before the user ever set it. First added for `/insights` (2026-08-14, priority #3), where it's applied per-day when scoring the 28-day window; a follow-up review found the same unfixed pattern in `/scores`, `/reports-weekly`, and `/reports-monthly` (copy-pasted before the fix existed, or — for `/scores` — assumed safe because it "only queries one day," which missed that `date` is a caller-supplied param, not always today) and applied it there too. `/reports-daily` doesn't need it: it always scores "today," and any goal that currently exists necessarily existed by today. `_shared/insights.ts`'s `computeInsights` takes a per-day `daily_score` series and produces per-KST-weekday averages (with best/worst) and a recent-7-days-vs-previous-7-days trend (`up`/`down`/`flat`, flat within a 3-point band to absorb rounding noise); both windows need at least one scored day or `trend` is `null`. A related fix: the weekly/monthly template's "N일 중" denominator is each goal's own scored-day count (`achieved+not_achieved+missing`), not the window size — a goal set partway through the window is only scored from then on, so a hardcoded 7/30 overstated it.

`_shared/day-breakdown.ts`'s `computeDayBreakdown` (added 2026-08-17) is a separate, goal-independent axis: given a day's logs, it needs a `wake` and a later `sleep` log to define the "awake span" (earliest wake to latest sleep), then splits that span into meal time and study time (both via the shared `sumPairedMinutes` — also what `scoreStudyDuration` uses internally now) and treats the remainder as "휴식 시간" (rest), clamped at 0 so a logging overlap can't produce a negative number. `averageDayBreakdowns` rolls a window of per-day breakdowns (nulls included) into a daily average for `/reports-weekly` and `/reports-monthly`, counting only days that had both a wake and sleep log. This is intentionally decoupled from `wake_time`/`study_duration` goal-scoring — a user with zero goals set still gets a breakdown-only report as long as they log wake/sleep, which changes each report endpoint's "no data" bail-out from "no goals" to "no goals *and* no breakdown."

**Day-boundary fix — wake-to-sleep sessions, not clock time** (2026-08-18, bug found via a user report: 기상/공부 data missing from reports while meal counts kept incrementing normally). Root cause: every endpoint that buckets logs "by day" used a fixed UTC-midnight boundary, which is 09:00-09:00 KST — any log before 9am KST (a very typical wake/study time) silently landed in the *previous* day's bucket and dropped out of "today." Switching the boundary to KST midnight alone doesn't fully fix it either: a user who sleeps past midnight KST would then have their `sleep` log split onto the *next* day, away from the `wake` that opened it — any fixed clock cutoff has this same failure mode for whoever crosses it while asleep. `_shared/day-sessions.ts`'s `computeDaySessions` replaces clock-boundary bucketing entirely: a "day" is now a session that opens on a user's first `wake` log and stays open — regardless of what day boundary it crosses — until the next `sleep` log closes it (a `wake` while a session is already open, e.g. a double-tap or nap, is folded into the current session rather than starting a new one). The session is labeled by the KST calendar date of its opening `wake`, since that's the date the user actually thinks of as "that day." `/scores`, `/reports-daily`, `/reports-weekly`, `/reports-monthly`, `/insights`, and `GET /logs?date=` all fetch a window of raw logs and then look up the relevant KST-dated session(s) rather than filtering by a clock range — see `docs/api-contract.md`'s day-boundary note under `/reports-daily` for the full user-facing explanation. `_shared/ai-report.ts`'s `dateOnly`/`dayRange` (used for the `ai_reports` cache-window check, not for log-to-day attribution) were also switched from UTC to KST for the same reason, paired with the `ai_reports` unique-index migration noted in Data model above. No response field names or shapes changed — only which logs get attributed to which day.

A same-day self-review (requested independently of the bug report, alongside a matching iOS-side sweep) caught two gaps in the first version of this fix, both since patched: (1) `/reports-daily` was still resolving "today" purely from the wall-clock KST date, so the documented sleep-triggers-report client flow (`POST /logs` for `sleep` immediately followed by `GET /reports-daily`) returned an empty report right when a late sleeper crossed KST midnight — the session that had just closed was labeled *yesterday* (by its wake), and by then the wall clock already said today. `resolveTodaySession` fixes this: it falls back to yesterday's session only when it's closed and its closing `sleep` log landed after today's KST midnight, and the response's `date` field reflects whichever day actually got scored. (2) `computeDaySessions` would fold every subsequent `wake` into an already-open session indefinitely if the user never logged `sleep`, silently merging multiple real days into one and losing wake_time scoring for all but the first; a session now closes itself (unclosed) and starts fresh if a new `wake` arrives more than 24h after the one that opened it.

**Cross-endpoint session-lookback fix** (2026-08-19, found during iOS integration testing on a live account that never logged `sleep`): each day-bucketing endpoint fetches only a bounded window of raw logs before calling `computeDaySessions` on that slice, and until this fix each endpoint used a different, endpoint-specific window start — `/reports-daily` fetched from *yesterday's* KST midnight (for the late-sleeper fallback above) while `/logs?date=` and `/scores` fetched from the queried date's *own* KST midnight with no lookback at all. That gap let the same log data get bucketed into different sessions depending on which endpoint answered: a still-open session (opened the evening before, no `sleep` logged since) fell inside `/reports-daily`'s window, so it correctly folded a next-KST-day `wake` into that same open session and reported no session for "today" — but that same `wake` fell outside `/logs?date=`'s narrower window, which independently (and wrongly) treated it as opening a brand-new session, so `GET /logs?date=` showed a `wake` log that `/reports-daily` said didn't exist for that day. `_shared/day-sessions.ts` now exports `SESSION_LOOKBACK_MS` (= the same 24h as the fold-window above, since a still-open session can only still be absorbing new `wake` logs — rather than being force-split — while they land within 24h of its original open) and every day-bucketing endpoint (`/logs`, `/scores`, `/reports-daily`, `/reports-weekly`, `/reports-monthly`, `/insights`'s `loadInsights`) now fetches starting at least `SESSION_LOOKBACK_MS` before its nominal window start, guaranteeing the windowed computation agrees with what running `computeDaySessions` over full history would produce. No response field/shape changes. Not covered by the pure-function unit tests (the bug was in each endpoint's fetch window, not in `computeDaySessions` itself, which was already correct given complete data) — verified instead by replaying the real log rows that exposed the bug through `computeDaySessions` directly, confirming `/logs?date=` now agrees with `/reports-daily`.

**`autoClosed` sessions** (2026-08-19, same-day follow-up, product decision): the account behind the fix above never logs `sleep` at all, which the previous fix left as a *correct but permanent* dead end — a `wake` with no `sleep` since stays open forever (unless a later `wake` more than `MAX_SESSION_MS` after the original one force-splits it), so that day's session, and anything checking whether it's "done," never resolves. `computeDaySessions(logs, nowMs = Date.now())` now also force-finalizes a still-open trailing session once `MAX_SESSION_MS` (24h, the same threshold as the existing wake-triggered split, not a new number — `SESSION_LOOKBACK_MS` above is a separate, differently-motivated constant that happens to share the value) has elapsed since it opened, setting a new `autoClosed: true` flag distinct from `closed` (which still means "a real `sleep` log ended this" and is untouched by the timeout). No synthetic `sleep` row is written to `routine_logs` — that table is a log of real user actions, and fabricating one would corrupt it (and be user-deletable, which a fake entry shouldn't be) — so this is a purely computed, unpersisted flag, freshly evaluated on every request against the real current time. `daily_score`/`computeScores` are unaffected either way since they only read `session.logs`. `time_breakdown` deliberately stays `null` even once `autoClosed`, for the same reason `computeDayBreakdown` already requires a real `sleep` log elsewhere in this section: there's still no real bedtime to report, and guessing one contradicts the "no data → say nothing" convention used throughout (see `scoreCredit`'s "missing always gets 0" comment). No endpoint currently exposes session open/closed state in its response at all (`GET /logs?date=` returns a bare log array; `/scores` doesn't include session metadata) — surfacing `autoClosed` to a client would be a genuine new response field and hasn't been added; flagged to the iOS team as a follow-up if the app wants to show it.

Covered by unit tests (98 cases total across `computeScores`, `computeDailyScore`, `goalsExistingBy`, `computeInsights`, `computeDayBreakdown`, `computeDaySessions`, `resolveTodaySession`, `deriveDailySuggestedAction`/`deriveWindowSuggestedAction`, `extractSuggestedAction`, `dateOnly`/`dayRange`, and the report builders) plus live-endpoint verification.

### AI feedback (`/reports-weekly`, `/reports-daily`, `/reports-monthly`)
Was the highest-risk component on the timeline; now implemented with the planned fallback: rule-based template report ships whenever Claude generation isn't available or fails, with real LLM generation (`claude-haiku-4-5-20251001`) used when it succeeds. Reports are generated at most once per KST day and cached (`cached: true` on repeat calls same-day). `/reports-daily` (added 2026-08-14, priority #2 in the post-launch feature list, response shape confirmed with the iOS team) is the same policy scoped to today instead of the last 7 days — its content narrates that day's `daily_score` and per-goal status. `/reports-monthly` (added 2026-08-14, priority #5, the final post-launch item) is a **rolling 30-day window, not a calendar month** — consistent with weekly's rolling 7 days and daily's "today", and avoids a misleadingly partial report for anyone who joined less than a month ago; it reuses `summarizeWeek()` (genuinely generic despite the name) for the count aggregation and adds a `date_range` field (`{from, to}`, same naming as `/insights`) since a single date doesn't make sense for a 30-day span. The Claude API call and KST-day-range helpers live in `_shared/ai-report.ts`, shared by all three functions to avoid duplicating that logic.

**Priority #4 — pattern-aware feedback** (added 2026-08-14): all three report endpoints call `loadInsights` and splice `describeInsights`'s output (best/worst weekday, recent-vs-previous-week trend) into the template fallback (a "패턴 분석" section) and the Claude prompt (extra context lines), so feedback references patterns instead of only the current period's raw counts. This doesn't change any endpoint's response shape — `content` is still a plain string, just written with more context. Pattern loading is treated as an enrichment: a `loadInsights` failure is logged (`console.error`) and the report still generates without it rather than 500ing — core report generation shouldn't depend on the enrichment succeeding.

**Day time-breakdown section** (added 2026-08-17, iOS-requested): all three report endpoints also splice in `describeDayBreakdown`/`describeAverageBreakdown`'s output as a "하루 시간 분배" / "일평균 시간 분배" section, additive alongside (not replacing) the goal-scoring section. `/scores`, `daily_score`, and `/insights` are untouched — this started as a report-content-only addition with no new response fields, but a same-day follow-up request (iOS wanted a "how was today spent" chart, which needs numbers rather than parsed prose) added a structured `time_breakdown: { active_minutes, meal_minutes, study_minutes, rest_minutes } | null` field to all three responses. It's computed via `toTimeBreakdownField`/`toAverageTimeBreakdownField` and **stored in `ai_reports` at generation time** (a new nullable `time_breakdown` jsonb column) rather than recomputed on cache hits, so a cached report's chart numbers always match what its own text describes rather than drifting from logs added later that day. "취침 로그 → 그날 리포트 트리거" is handled client-side (iOS calls `GET /reports-daily` right after the `POST /logs` for `sleep` succeeds) rather than as a backend side effect, consistent with the Notification philosophy below.

**Prescriptive `suggested_action` field** (added 2026-08-18, iOS-requested): part of a broader "descriptive → prescriptive" push — the app should tell users what to do next, not just what happened. All three report endpoints now also include `suggested_action: string | null`, a single concrete next-step sentence pointing at the user's single biggest loss (lowest-scoring goal), for iOS to render as a standalone highlight card rather than parsing it out of `content`'s free text. For the Claude path, `buildDailyClaudePrompt`/`buildClaudePrompt`/`buildMonthlyClaudePrompt` instruct the model to end its response with a lone `ACTION: <sentence>` line, which `_shared/ai-report.ts`'s `extractSuggestedAction` strips off and returns separately (so it never appears twice, once in the card and once in the body). If Claude omits that line, or the template-fallback path is used, `_shared/suggested-action.ts`'s `deriveDailySuggestedAction`/`deriveWindowSuggestedAction` computes the same field with a rule (worst-`scoreCredit` goal for daily; lowest achieved-day ratio for weekly/monthly), reusing `scoreCredit` (now exported from `scoring.ts`) rather than re-deriving per-goal closeness. `null` when there are no scorable goals or everything's already achieved — same "nothing to say" convention as `time_breakdown`. Stored in `ai_reports` at generation time (nullable `suggested_action` text column) for the same cache-consistency reason as `time_breakdown`.

### Notification philosophy
Notifications are deliberately pushed to the iOS client to compute locally rather than being server-driven, to keep server load down. Don't build server-side notification scheduling unless this decision is revisited.
